Ambient reliability metrics: analysis so far

Frontend reliability metrics for the Q4 OKR draft. Written 2026-10-15 from the work in this session. Every number below comes from a query, a CSV, a Sentry/Crashlytics page or a code read that is named next to it; inferences are labeled as such.

Summary

  • Unexpected Recording Failures (0.12%, goal 0.01%) is mostly measuring something else. 70% of the failure events in a 4-day sample are "No microphone detected", which the Notion definition calls expected but the SQL counts as unexpected. Excluding them, the rate is about 0.035%.
  • The database problem is captured, mostly by Unexpected Failures. "Failed to save/retrieve recording data" is 13% of failure events and Sentry places it in the local cache write path (CacheRepository.insertAudioCache, insertFilePart). Fixing local storage would plausibly cut the rate left after the mic reclassification by about half (0.035% to about 0.018%). My earlier per-user check found no extra scribe loss, but that test was weak (section 3), so effects on lost scribes, stuck-in-cache and audio discrepancy are untested, not ruled out.
  • "% of scribes succeeded in uploading or recovered" is not a whole-flow metric. It is a recovery rate for recordings whose local cache was seen paused or error. It does not cover recording start, scribe status, audio completeness or note completion. My earlier recommendation of it as a headline KR was too strong.
  • App kills are mostly invisible to the recovery metric (36% of killed recordings), but they rarely lose the whole scribe. Of 709 invisible killed recordings in one day, 683 already had a scribe row and only 26 never got one.
  • On Android, two crash groups drive the picture: a flat foreground-service crash (about 16 users a week) and spiky Intune/MAM crashes that began around Sep 14. Neither appears on the latest build (3.42.0), but almost nobody is on it yet.
  • The background-kill complaint is real, and it shows up as missing audio, not lost scribes. On Oct 6, about 8% of active mobile kills left a scribe with more than 10 seconds of audio missing (about 46 recordings a day, 0.1% of mobile scribes), 20-30 times the normal rate. It is a slice of Audio Discrepancy that the web-dominated headline hides, and the recovery metric counts it as a success.
  • Proposed Q4 KRs (section 4): Lost Scribes, mobile audio gap after an app kill, Android crash-free users, and Unexpected Failures redefined without microphone failures.

2. Unexpected Recording Failures

How the rate is calculated checked in code

% Unexpected Recording Failures = failed / attempted (reun_all_metrics.js). failed is the sum of COUNT(*) of SCRIBE_FAILED events from get_scribe_failed_metrics.sql, with internal accounts removed and only two "recording too short" reasons excluded. attempted is scribes + lost + netStuck + failed, so failed sits in both the numerator and the denominator.

  • It counts events, not distinct scribes. A retrying user can log several failures for one session.
  • failure_reason NOT IN (...) is NULL for events with no reason, so those events are silently dropped.
  • Per-platform rows drop web rows with no browser_name, so they may not add up to the rollup.
  • Sanity check: 345 events in 4 days is about 600 a week; at roughly 400K scribes a week (Q4 doc) that is about 0.15%, in line with 0.12%.

5. The recovery metric: what it really measures

% of scribes succeeded in uploading or recovered is computed in get_scribe_cache_health_recovery_aware.sql and the rollupSpecs in reun_all_metrics.js.

  • Denominator: distinct recordings whose local cache was seen in state paused or error in at least one SCRIBE_AUDIO_CACHE_HEALTH_V3 check-in, counted once at first sighting, with the cache created inside the window. This is a state seen in a check-in, not a "user tapped pause" event, and error is included.
  • Numerator: those recordings that later have a row in the server scribe table between cache creation and the end of the week. Recordings still uploading at the cutoff count as not recovered.

Which stage of the flow does it cover?

StageCovered?Why
Recording startsNoStart failures and sessions that never began are not in the population.
Audio recorded to local cachePartlyOnly if the cache was later reported paused or error.
UploadPartlyA crash or closed tab sends no check-in, so it never enters the population (it shows up under lost scribes instead).
Scribe creationWeaklyA scribe row "exists"; its status and audio completeness are not checked.
Transcription and note completionNoNothing looks past the scribe row.
  • The worst failures are excluded (crashes and closed tabs send no check-in).
  • It counts missing audio as success. "Recovered" only means a scribe row exists. After a background kill the user resumes, a scribe lands, and the earlier audio is missing; the metric calls that recovered (see section 6).
  • "Paused" includes normal behavior: a clinician pausing mid-visit is also paused. If they resume and finish they count as "recovered", which pushes the rate toward 100%. I could not size this effect; what sets the paused state in the app was not confirmed.
  • The group size does not reconcile: stuck-in-cache is 1.97% of attempts while 2.7% of the "ever stuck" group went unrecovered. Those only fit if the group were most of all scribes; they come from different queries.
  • A second similar metric ("% Scribe Recovered After Stuck in Cache", goal 90%) uses a different calculation; the doc's 97.30% and goal 99% belong to the one described here.
  • It is per recording, not per chunk; the Q3 notes plan to move to "% chunk recovery".

For a whole-flow KR the shape would be a funnel: started, recorded, uploaded (scribe row), audio complete (no discrepancy), note completed, with a rate at each step. Today's metrics each cover one slice and nothing covers completion. I did not check whether the scribe table's status columns support the last step.

6. Are app kills captured by the recovery metric?

Input: app-kill-oom-sql, which counts APP_KILLED_DETECTED events for recordings that were still active. It does not detect out-of-memory; it counts any detected kill. Cross-check run in Retool for kills detected on Tue 2026-10-06 (CSVs 003, 004, 005 (kill cross-check) and 006, 007 (audio gap); lite queries without the "active" filter, internal accounts included).

Code read

  • Lost scribes requires error_events = 0, and APP_KILLED_DETECTED counts as an error event, so a killed recording is never counted as lost.
  • Unexpected failures counts only the SCRIBE_FAILED tag, so kills are not counted.
  • Recovery metric sees a kill only if the cache was observed paused or error.

  • The recovery metric does miss most background kills: only 22-26% of iOS/Android background kills enter its population, and 38-46% of them are invisible by that definition.
  • The cost of that miss looks small for scribe existence. Only 26 of 1,988 killed recordings (1.3%) have no scribe ever, which is the same order as the lost-scribes figure of roughly 11 a day.
  • There is no upload-to-scribe-creation hole in this sample. All 465 recordings with a finished upload have a scribe row.
  • Most "kills" are likely not interrupted recordings: 683 of the 709 invisible ones already had a scribe row from before the day, so the kill event probably points at the app's last, already-finished recording (inference).
  • Where the metric does see kills it looks worse than the headline: 597 of 661 recovered (90%) vs 97.3%.

Do kills leave scribes with missing audio? the customer complaint

Customers report: they record in the background, the app is killed, they reopen it and it shows "paused", they resume, and the audio from before is missing. That is a scribe that lands with a gap, which none of the checks above measure. Test: compare client recording length (the PARALLEL_RECORDING_ENDED payload) with server audio_length_in_seconds, using the same rule as Audio Discrepancy (client more than 10 seconds longer).

  • Audio Discrepancy does see the complaint on mobile. Killed mobile recordings are about 20-30 times more likely to have a gap over 10 seconds, so the client's recording_length must still include the lost pre-kill time.
  • Most active kills do not lose audio (about 92% show no gap over 10s); the loss is concentrated in about 8%. Two levers: how often active recordings are killed (1.4% of mobile scribes on this day) and how often a kill leaves a gap.
  • Size: about 46 recordings a day over 10 seconds and about 18 over 60 seconds. A rough weekly scale-up is about 320 and about 125 (one Tuesday, so approximate). Lost scribes is about 11 a day for comparison.
  • The headline hides it. Web is about 90% of recordings with a gap over 10 seconds on this day, and mobile kills about 5%. Mobile Audio Discrepancy overall is about 0.2%, already under the 0.5% goal. A goal on the headline would not reflect this complaint.
  • The recovery metric counts these recordings as successes (a scribe row exists), so it cannot serve as the KR for this problem.

Proposed metric: "mobile recordings with an audio gap after an app kill", reported as a count and as a share of mobile scribes, with the over-60-second count as the severe version. It is a slice of Audio Discrepancy (same gap rule), so report it next to the headline. Queries: 20261015-kill-audio-gap-metric-day.sql (one day, untested at week scale; the week version timed out). A more direct measure needs the app to log expected vs recovered audio seconds on resume after a kill.

Limits: one day; the gap only counts client-longer cases and ignores gaps under 10 seconds; 24 active kills never landed a scribe and 62 landed without an end event, so they sit outside the numerator; resumes after Oct 9 are not captured. Crashlytics also does not show OS process kills as crashes (general platform behavior, not confirmed for this app).

  • Foreground service (ForegroundServiceDidNotStopInTimeException, muted since 3/31): a flat floor of about 16 users a week. Android shuts the app down when its background service (data-sync type, our flutter_background_service) does not stop within its time limit. In the latest week 100% were in the background, 78% Samsung, 56% Android 16. At roughly 2,400-2,800 active users it alone caps crash-free users near 99.3-99.4%, against the Q4 goal of 99.39%.
  • Intune/MAM (seven issues in Microsoft's MAM SDK screens, all "early crashes" at launch): zero in Sep 7-13, then 102 events the next week, 14, 54, and 10. Something changed around Sep 14; not yet investigated.
  • In Oct 5-11 these two groups were 74% of 38 crashes (foreground 47%, MAM 26%).
  • Versions, Oct 5-11: 3.41.0 15 events, 3.40.2 17, 3.40.0 2, old 3.29-3.32 4 (out-of-memory), 3.42.0 zero. But filtering to 3.42.0 shows no sessions at all in that window, so the latest build had essentially no users yet and the zero is not evidence of a fix.
  • Out-of-memory crashes are negligible on Android (5 of 360 over six weeks), so the Q3 "low memory" explanation applies to iOS, not Android.

8. Caveats and next steps

Caveats

  • The StarRocks mirror reachable from the Claude skill stops at 2026-08-28 (scribe_events has no rows after that, while other tables are current). All event analysis above therefore used Retool's connection. The pipeline owner should check why the mirror stopped, and whether the Retool resource reads the same warehouse.
  • Samples are small: 4 days of failures, 1 day of kills, 82 Sentry users, one week of per-issue Crashlytics detail. Internal accounts are included in the ad-hoc queries (not in the dashboard).
  • The Q4 baselines in the OKR doc may not be freshly computed.
  • A SQL correction for Unexpected Failures (exclude microphone failures, fix the NULL failure_reason hole) was opened as PR #1 and then closed and reverted. The dashboard query is unchanged.
  • Weekly active user counts are back-calculated from Crashlytics percentages, so they are approximate.

Suggested next steps

  • Decide whether "No microphone detected" belongs in Unexpected Failures; re-baseline, then set the goal.
  • Size the recovery metric's population: split first-stuck recordings by paused vs error and compare with recordings started. This shows how much of 97.3% is normal pausing.
  • Run the one-day kill audio-gap query for more days to firm up the baseline (0.1% of mobile scribes, 8% of active kills), and split it by background vs foreground, app version and time before the kill.
  • Investigate what changed around Sep 14 for the MAM crashes (releases, rollout, enterprise onboarding) and which service the foreground-service crash is.
  • Check 3.42.0 (1013) rollout in Firebase Release Monitoring.
  • Fix the NULL failure_reason hole in get_scribe_failed_metrics.sql (no code has been changed so far).
