Smart Update audio is lost when the upload is cut off

Smart Update sends the whole recording in one request, with no saved record, no retry and no timeout. If iOS suspends the app mid-upload, the audio is gone and the provider is never told. This page covers the problem, the proposed solution, and the options we dropped.

3As-is vs to-be

Same submit tap, different outcome when the upload is cut off.

As-is: nothing records that the upload was started, so a cut-off leaves no trace and no recovery.

4Proposed solution

Log what happens, make a stalled upload fail visibly, and keep a record of every pending upload so it can be resent.

PartWhat it does
Events UPLOAD_STARTED (upload id, file size, recording length), saved on the phone first so it survives the app dying right then. upload_id, upload_duration_ms and file_size_bytes on the existing SUBMITTED / FAILED / RATE_LIMITED. error_type on FAILED. A cut-off upload is an UPLOAD_STARTED with no outcome for the same upload_id.
Send timeout sendTimeout on regenerateWorkflow, so a stalled upload fails instead of hanging.
Pending list + retry
iOS / Android audio only		 Append an entry (with the user id) to a JSON list before the POST; remove it and delete the file on 200. On launch / resume, retry each entry one at a time, up to N attempts. Event: RETRY_ATTEMPT. The list survives logout, only the recording user is retried or prompted, and entries older than 7 days are dropped with their audio.
Tell the provider When an entry runs out of attempts: Try again / Dismiss (Dismiss deletes the file). Events: RETRY_EXHAUSTED, USER_NOTIFIED, USER_RETRY, USER_DISMISSED.
Background retry
optional, later		 Run the retry from the existing Workmanager job. Only worth it if the new events show uploads still sit unsent until the next app open.

No database migration and no generated code.

Where it stores things
  1. Pending list: one JSON value in SharedPreferences (SharedPrefParams), key pending_smart_update_uploads. Plain text is fine: it holds IDs, a section key and a file path, no patient data.
  2. Audio: stays where the recorder wrote it, Documents/scribe_audio/. The fix only stops it being deleted until success or Dismiss.

A list, not a single value, so a second failed update doesn't overwrite the first.

Mobile is 42% of Smart Update opens (5,669 of 13,411); web and Chrome are 58%. On web the recording is held in memory as bytes, so there is no file to retry from. The events still ship on web, and an UPLOAD_STARTED with no outcome event will show how many web uploads are really cut off, as opposed to people leaving the screen. That decides whether web needs its own fix.

Rules
  • Remove an entry only after the server answers 200.
  • If the audio file is gone, drop the entry and log it.
  • No patient names or note text in events or in the pending list.
  • Text-only updates (typed context) are not saved; they are small and finish fast.

5Alternatives we dropped

Click a card to see why.

New drift table for pending uploads dropped

A dedicated PendingSmartUpdateTable with a migration (schema 9 → 10).

  • Needs the full migration ritual: schema bump, regenerated .g.dart, schema snapshot, stepwise migration, migration test.
  • Adds roughly 1.5k generated lines to the PR, which makes review harder.
  • A failed migration affects every existing install, for data that is a handful of IDs and a path.

Can revisit if the pending record ever needs PHI (e.g. saving typed context), which would need encrypted columns.

Reuse ScribeCacheTable dropped

Store the pending update as a row in the scribe cache.

  • The chunk retry service and cache_repository.dart pick rows up by state, so a Smart Update row would be retried as a scribe.
  • The lost-scribe and stuck-in-cache metrics count these rows, so they would be skewed.
  • Avoiding that needs a type column and a filter in about 9 files.
  • templateIdsAsString is non-null, so the row doesn't even fit.
Reuse FailedEventTable dropped

Park the pending update in the failed-events table.

  • EventRetryService would try to send the row as a scribe event.
  • The table has one text column (eventData); we'd overload it with a different meaning.
Chosen: JSON list in SharedPreferences chosen
  • No migration, no generated code.
  • No overlap with scribe cache metrics or the event retry path.
  • Content is IDs and a path only, so plaintext prefs are acceptable under the storage tiers in CLAUDE.md.

6Out of scope & open questions

Out of scope
  • Resend on web / Chrome extension: audio is in-memory bytes and doesn't survive a reload, so the pending list can't cover it. Needs a separate design (e.g. IndexedDB with encryption). Events and timeout still apply.
  • Re-eval branch (/workflow_task_re_eval): same gap, not in the ticket. The pending entry can take a branch field later.
  • Keeping the upload alive in the iOS background: would make cut-offs rarer but not recoverable; possible later add-on.
Open questions
  • Web and Chrome are 58% of Smart Update opens. Do we wait for the new upload events to show how many web uploads are really cut off, or design a web fix now?
  • What should N (max attempts) be?
  • Do we build the background retry, or wait for data from the new events?
  • Should re-eval audio be included, or follow up later?
