Bars use different sources and definitions, so read them as "which part of the picture", not a precise ratio. Sentry counts kills it classifies as memory/watchdog; APP_KILLED_DETECTED counts every session that ended without a clean stop.

2. iOS memory kills: how it is extracted

  1. Kills (numerator). Sentry issue SCRIBE-MOBILE-B0, event type WatchdogTermination. Sentry infers the kill on the next launch from the previous session: the app was open, then vanished with no crash. It is counted only if the app was in the foreground. Pulled from the Sentry export in BigQuery (unified_monitoring.source_metrics), PRODUCTION only, summed per UTC Mon–Sun week and release.
  2. Recordings (denominator). Count of scribe rows with device_type = 'MOBILE_IOS' per week and app version, on the Postgres read replica, internal accounts excluded.
  3. Rate = kills ÷ recordings, per week and per version.
Show the queries 
-- kills per week and release (BigQuery, read-only)
SELECT CAST(DATE_TRUNC(DATE(timestamp), WEEK(MONDAY)) AS STRING) AS wk,
       COALESCE(REGEXP_EXTRACT(release, r'@(.*)'), '(no release)') AS ver,
       SUM(event_count) AS kills
FROM `athelas-scribe-mobile.unified_monitoring.source_metrics`
WHERE source_issue_key = '<the SCRIBE-MOBILE-B0 key>' AND environment = 'PRODUCTION'
  AND timestamp >= TIMESTAMP('<first Monday>') AND timestamp < TIMESTAMP('<Monday after the report week>')
GROUP BY 1, 2 ORDER BY 1, 3 DESC;

-- recordings per week and version (Postgres prod replica, counts only)
SELECT date_trunc('week', s.created_at)::date AS wk, s.version, COUNT(*) AS n
FROM scribe s
WHERE s.created_at >= '<lo>' AND s.created_at < '<hi>' AND s.device_type = 'MOBILE_IOS'
  AND NOT EXISTS (SELECT 1 FROM scribe_accounts a WHERE a.id = s.scribe_account_id
       AND (LOWER(a.email) LIKE '%commure%' OR LOWER(a.email) LIKE '%athelas%' OR LOWER(a.email) LIKE '%augmedix%'))
GROUP BY 1, 2 ORDER BY 1, 3 DESC;

Known limits: background kills are not counted; some non-memory watchdog kills (for example a hang) could be included, though Sentry's own rules exclude crashes, OS updates, reboots and user force-quits; iOS reports no unique-user count here, so one device killed 80 times counts 80 times.

3. Android OOM: how it is extracted

  1. Events (numerator). Sentry OutOfMemoryError events in the scribe-mobile project, filtered to os.name = Android, counted per UTC Mon–Sun week. Search used: error.type:OutOfMemoryError os.name:Android with fields timestamp, user, device, release and issue, over about 7 weeks. This reproduced the previously published row exactly (6, 3, 1, 7).
  2. Recordings (denominator). Count of MOBILE_ANDROID scribes for the week from the same Postgres query (21,888 for 11/2–11/8).
  3. Distinct users are reported next to the count, because one phone can produce most of a week's events: in the 10/26 week 6 of 7 events came from a single phone.
What it misses. It only counts out-of-memory errors that the app itself catches. When Android's low-memory killer ends the whole process, nothing is thrown and nothing is logged. On the one phone we traced, the app died about every 7 minutes and Sentry saw roughly 1 in 7 of those deaths. So the Android number is a floor, and a low one.

Same week, 11/2–11/8: iOS had 4,285 all-cause kills vs 1,052 Sentry memory kills (about a quarter); Android had 324 vs 3. For iOS that means the Sentry figure is a subset of all unclean endings, not a ceiling. Different sources, so the ratio is indicative only.

5. How to read and use them

  • Track each row against itself week over week. The iOS trend (0.38% → 0.44% over five weeks) is meaningful; the Android row is too small and too noisy to trend (one phone can swing it).
  • Do not compare iOS with Android. They measure different things; 0.44% vs 0.014% is mostly a difference in what is counted, not in health.
  • Concentration matters more than the rate. A few dozen repeat-kill devices produce most of the iOS count; see the kill-loop analysis.
  • Suggested wording for the report: "iOS counts foreground memory kills only, so it is a lower bound. Android counts only out-of-memory errors the app catches, so it is a lower bound. All-cause app kills are the ceiling."

6. Making the numbers better

  1. Android exit reasons (LLM-21376, in testing). The app will record why the previous process died (Android 11+): low memory, crash, ANR, user-requested and so on. Counting exit_reason = low_memory kills from APP_KILLED_DETECTED would replace today's guess with a real Android memory-kill number.
  2. iOS memory outside recordings (AFEP-3047). Periodic memory capture after the recording ends would explain kills that Sentry cannot see in the foreground.
  3. Per-recording linking (AFEP-3003, done). Tagging each Sentry kill with the recording it interrupted lets us measure how many recordings are cut short, not just how many kills happen.

Caveats

  • Numbers are from the weekly report for 11/2–11/8; Android OOM counts are per Mon–Sun UTC week and read from Sentry on 11/10.
  • iOS kills come from the Sentry export in BigQuery; the all-cause kill counts come from scribe_events, which only the user can query in Retool, so the two sources use different definitions.
  • The Android all-cause figure (324) counts detected kill events for the week, not unique recordings.
