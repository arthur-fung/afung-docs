Why does a scribe end up “INCOMPLETE”?

A plain-language guide to the code paths, combined with the findings from Ambient Frontend Reliability 10/19–10/25.

INCOMPLETE is not a crash. It means the recording reached us, but there was nothing usable to write a note from. The provider sees a scribe with no note.

There are two reasons a scribe gets this status. The code checks for them in seven places (see the next section).

1. “No speech detected”
607
this week (70%). The audio file was there, but our transcription service heard no one talking. 412 of these had 30 s or more of audio, so the mic was recording silence.
2. “Not enough info in the transcript”
261
this week (30%). Someone talked, but the transcript had fewer than 10 words (5 for nursing accounts). Usually a very short recording.

What “recording silence” looks like

Deep dive on account 273882 (11 “no speech” scribes on WEB_APP - CHROME 7.11.x). Hover the bands.

Recording and upload worked

Every recording had 1 valid audio part and a file size that matched its length.

The mic was on, but nearly silent

Not muted (above −150 dBFS) but 40+ dB quieter than speech. This fits a wrong input device or zero gain.

The warning didn’t stop anyone

LOW_AUDIO_DETECTED fired in 9 of 11 recordings (188 times). The provider finished anyway, and retried 6 times in 30 minutes.

Things that might surprise you

Errors ≠ incomplete

Corrupt audio, audio under 1 second and unknown failures become ERROR, not INCOMPLETE. Only “no speech” and “too few words” become INCOMPLETE.

Regenerating can make a note INCOMPLETE

If a provider asks to regenerate a note and the existing note plus the request is under 10 words, the scribe flips to INCOMPLETE, with no reason message saved.

One errored chunk isn’t enough

With several audio parts, the scribe is only marked when every part failed transcription. If one part has speech, the note is generated from that.

Status can be half-updated

Some paths update the status but not the separate status ID column, and one marks the scribe INCOMPLETE while its tasks become ERROR. Queries on the ID column may undercount.

Where we could reduce incomplete scribes

Biggest lever · client

Make the low-audio warning blocking

Targets the 412 silent-mic scribes a week. Show the selected input device so the provider can switch it before the visit is lost.
Telemetry · client

Log input device and gain

Add them to PARALLEL_RECORDING_STARTED so we can confirm “wrong mic” instead of guessing from dBFS.
