Web app ignores quick clicks

AFEP-3009 / LLM-21079 · one provider on the web app (Edge and Chrome) · written 2026-11-17

Reproduced locally
In one sentence
A quick click does nothing (no ripple), but clicking and holding works. This is a known Flutter web bug that happens when the accessibility layer ("semantics") is on. We reproduced it by forcing semantics on in the browser console. Flutter has fixed it upstream, but the fix is not in any stable release yet. What we do not know is what switched semantics on on the provider's laptop.

1. What the provider sees

SymptomSwitching patients or dates does nothing on a normal click. No hover or ripple reaction in the video.
WorkaroundClick and hold works in both Edge and Chrome.
ScopeTwo computers, both browsers, started mid-October. Colleagues at the same site are fine. It is worse with the telehealth site (Doxy.me) open in the same browser.

Also seen on a teammate's machine: clearing only the browser's cached files fixed it, and it stayed fixed.

2. How a click should work, and where it breaks

1. Mouse down + upBrowser sends both to Flutter.
→
2. Flutter handles itRow highlights, tap fires, patient opens.

With semantics on, Flutter's click debouncer changes this:

1. Mouse down + upHeld back by the debouncer.
→
2. Browser "click" arrivesHeld mouse events are thrown away.
→
3. Substitute "accessibility tap"Sent to the centre of the element. If it does not land on the handler, the click is lost.

A quick click never reaches the button, so there is no ripple. A click-and-hold gets through. Flutter's own report #158530 describes the same thing ("it takes a long click for a click to register"). Why holding gets through is our reading of how the debouncer works; the Flutter reports do not spell it out. Matches the Flutter reports #158530, #147881, #188859.

3. Reproduction

Reproduced on a dev machine by forcing semantics on. Result: quick clicks fail, click-and-hold works. Same as the provider.

Steps (about a minute)
  1. Open the web app and log in (staging or a release build; avoid debug mode).
  2. In the DevTools console run: document.querySelector('flt-semantics-placeholder').click()
  3. Check it worked: document.querySelectorAll('flt-semantics').length is above 0.
  4. Quick-click a visit row or date chip: nothing happens. Click and hold: it works.
  5. Reload the page to switch semantics off again (it cannot be turned off in a running session).

Do not use SemanticsBinding.instance.ensureSemantics() for this: in debug mode on localhost it disables all text input (see the comment in lib/main.dart).

Not yet checked: whether the date picker and every other list fail the same way, and what turned semantics on for the provider.

5. Findings

The app is healthy underneath checked

The provider's client logs (one day, about 50,000 lines) show database calls in 5–70 ms, network checks all "good", event uploads succeeding and no errors near the time of clicks. Our code keeps running; clicks are not reaching the widget.

Heavy page reloading and several open copies noted

About 5 page reloads a day on one browser, and 4 browser instances seen in one day, two active at the same time (probably Edge and Chrome). Consistent with a person refreshing because the screen feels stuck.

Memory is normal ruled out

Browser memory while recording (Nov 2–17): about 100–130 MB on most days. One Edge-only spike on Nov 4 (peak about 856 MB) that did not repeat. The complaint started in mid-October, so memory does not explain it.

Average (blue) and peak (orange) browser memory per day, MB, recording sessions only.

Stuck tour overlay ruled out

Logs show no tour active and the user is not eligible for one.

Stale app files in the browser cache unlikely

Production sends max-age=0, must-revalidate for index.html, main.dart.js, flutter.js, the CanvasKit .wasm and our JS files, so old copies cannot be reused after a release. The service worker never stores anything. JSON files (such as version.json) can be reused for up to 1 hour. Open question: why clearing cached files fixed it for a teammate.

What we do not measure today gap

On web we send no CPU or GPU usage, no frame timings, no record of clicks that did not land, and no record of whether semantics is on. Only memory (while recording) is sent.

No past fix in scribe-mobile checked

Nothing in the repo history fixes this symptom. The closest is a Copilot-input focus fix (#5883, Aug 31), which is a different bug. Existing open reports of dead Assistant input boxes (LLM-20436) may share the same cause; worth checking once the log exists.

7. Recommendation

Ship soon Short-term workaround

Remove the hidden flt-semantics-placeholder element for flagged accounts, so nothing can switch semantics on. About 10 lines of JavaScript plus a per-account flag; we can release it ourselves.

Cost: screen-reader support stops working for flagged accounts. Turn it on for the affected provider only. Local test: remove the element before clicking anything and check the semantics element count stays at 0. Not yet checked: that it fully protects a real session on the provider's machine.

Wait for release Real fix: upgrade Flutter

Move to Flutter 3.51 stable, which includes flutter#191529 and fixes this for everyone. It is a big jump from 3.47 (QA on all four builds). Optionally ask Flutter for a cherry-pick into 3.50.x.

No stable release has the fix today; the first one with it is the 3.51 beta.

  1. Build the workaround behind a per-account flag and turn it on for the affected provider.
  2. Log whether semantics is on (startup and every change, plus a Mixpanel property web_semantics_enabled). This shows who else is affected and whether the workaround helped. It needs nothing from users.
  3. Open the Flutter upgrade ticket for 3.51 stable.
  4. Check other screens. Confirm the date picker and other lists fail the same way. If so, the earlier idea of changing the visit row hover is not the answer and can be dropped.
  5. Do not disable semantics for everyone: it fixes clicks but breaks screen-reader support.

Still unknown: what switched semantics on for this provider (screen reader, dictation tool, browser extension?). The log above will not name it, only show that it happened.

Sources: Flutter issues #158530, #147881, #195812, #195291; PRs #191529, #192641. Provider identity, site and account IDs are left out on purpose.
