1. What a loop looks like

Each recording logs the app’s memory every 30 seconds. On one Android phone (one account, one recording, one hour) the memory climbs about 300 MB every 30 seconds to ~4.2 GB, the process dies, relaunches within a minute, and starts again. The recording keeps its identity across the 7 restarts.

4. Is it the torn GCP log cache?

The hypothesis. scribe-mobile PR #6488 (merged to develop 11/9, not in 3.43.1) fixes a bug where a kill mid-write cuts the on-disk log cache file inside a multi-byte character. The strict read then threw on every flush, each failure logged an error that fed back into the cache, memory grew until the OS killed the app, and the device shipped no client logs. A kill tears the file, the next launch reads the torn file and climbs, so a device can stay in the loop. The PR documents this on iOS; the same trigger exists on Android.
EvidenceReading
Climb starts shortly after launch, regardless of screen or audio; Java and native heaps flat (growth is on the Dart/other side)Fits
Loop devices ship far fewer client logs: Android account ~552 entries in 6 h vs ~11,300 median for healthy accounts; iOS climbing accounts median 2,707 vs 13,000; 4 of 15 climbing iOS accounts shipped zero while actively recordingFits not conclusive

5. What we ruled out

CandidateWhy not
Audio capture or bufferingBoth the loop account and a healthy one flush an identical 2.64 MB chunk every 30 s (44.1 kHz mono). The recording’s whole audio is about 5 MB a minute; memory grows ~600 MB a minute.
Upload backlog or failed flushes107 of 107 chunks uploaded on schedule during the loop.
An event stormNo event type fires at an abnormal rate (about 2 chunk events a minute, normal).
Reading all saved audio on each restartThe first cycle of the recording climbed as fast as later ones, with only a few minutes of audio saved.
The phone model aloneA second phone of the same family on the same build held 290–340 MB across several recordings.
A fleet-wide leakA quarter of Android accounts for an hour: only the loop account climbs; everyone else peaks under ~470 MB.
Ordinary Java heap OutOfMemoryThe Java heap stays at 6–30 MB during the climb. Sentry’s OutOfMemory errors catch about 1 of 7 deaths on the loop phone, so they undercount.

6. How to confirm, and what to do next

  1. Test-phone repro (decisive, hours). On a debug build of 3.43.1, append an incomplete emoji to the log cache file, relaunch, and watch memory. A climb of ~10 MB/s confirms it; then repeat on develop with PR #6488 and it should stay flat.
  2. Re-measure after the fix ships. Re-run the repeat-kill count, the memory-peak check on the same accounts, and the log-volume count. Peaks should fall to about 300 MB and log volume should recover. The fixed code also logs “Skipped N malformed cache entries”, which counts devices that actually had a torn cache.
  3. Ask which release carries PR #6488.
  4. Android exit reasons (LLM-21376). Once shipped, the kill event records why the process died, replacing today’s guess for Android.
  5. Optional: check the 8 untested top-25 iOS users (17% of events) the same way.
For the weekly report: “A few dozen repeat-kill devices account for roughly 57–74% of iOS memory kills; a candidate fix is merged but not released, and the cause is not yet confirmed.” The Android OOM row measures mostly one phone.

Method and caveats

  • Kill counts: Sentry iOS memory-kill issue (7 days to 11/9) and APP_KILLED_DETECTED in scribe_events (11/2–11/8). They use different definitions, so shares are compared within a source.
  • Memory samples: the app’s 30-second resource samples; iOS reports physical footprint, Android resident memory, so each platform is compared with itself.
  • The sampled checks cover one hour or one 6-hour window on 11/9 and a subset of accounts. “Untested” means not checked, not clean.
  • Log counts are entry counts per account from Cloud Logging (no content read); capped at 20,000.
  • Account and user ids, recording ids and device ids are replaced by labels in this page.
