Missing in the v2 API

  1. No list of all site providers with provider_id. Every write that takes providers needs provider_id. The only full list the screens have is site_user_template_assignments, which returns scribe_account_id, scribe_account_email and provider_name; the backend joins Provider but doesn't return its id (admin_panel/services.py, get_site_user_template_assignments_service). /providers, /template_coverage and /missing return provider_id but only subsets. A provider can also have more than one scribe account, so keying by account can list someone twice. Smallest fix: add provider_id to each row of site_user_template_assignments.
  2. No atomic "move and re-template the source rule". Only needed if Move keeps its step 2 (#12).

Decisions

  1. v0 is acceptable. Using v0 doesn't fail a row on its own; the Check column scores behaviour only.
  2. v2 swap is the plan. Replace the v0 view model with the v2 client (AppointmentRulesV2Repository, already on develop from #6358), and use missing_rules / GET /missing instead of the client-side counts. That fixes rows 1–4, 9 and 16. Anything the screens need that v2 can't provide is listed under "Missing in the v2 API".
  3. Move, step 2 is a change of template on the source rule. Its copy matches the change-template confirm ("N providers currently use this template. Which template should they use instead?"), so it maps to a second write: §5.3 PATCH /{source} with new_template_id, after §5.4 PATCH /{target}/providers.

Open question for Prokash

  1. Keep Move step 2? The spec's move doesn't need it: the other providers stay on the source rule, and the rule is deleted only if the moved provider was its last one. Keeping it means two non-atomic writes (see "Missing in the v2 API" #2). The spec does ask for a confirm before moving a rule's last provider (§5.4), which the flow doesn't have. Keep step 2, or replace it with that last-provider confirm?
  2. Move doesn't ask about providers without the target's template. Add the providers_without_template choice (ADD_TEMPLATE / PERSONAL_RULES), as Delete already does.
