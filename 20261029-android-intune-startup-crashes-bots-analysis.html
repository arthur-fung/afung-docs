The top two Android crashes are automated testers, not clinicians

YubiKeyPromptActivity.onMAMCreate NullPointerException and MAMResolverActivity.onMAMCreate NullPointerException (both Intune MAM) top the 3.42.1 crash list. Every one of these crashes traces back to two devices that behave like an automated test fleet. No evidence points to a real user.

0
real users affected
Verdict: automated testing (most likely Google Play app review)

Eight independent checks all point the same way. The strongest:

(1) Play's Android vitals, which counts only real users, shows neither crash.
(2) The 3.42.1 crash burst happened on Oct 23, two days before the build was public (released Oct 25).
(3) One of the two devices reports an x86_64 CPU on a phone that only exists as ARM, so it can only be an emulator.

1Only two device models have ever hit these crashes, and every install on them crashes›

Across 90 days, every single event comes from one of two device models, both reporting Android 11. Across our 2,204 weekly Android users, no other model has hit either crash even once. On 3.42.1, every install on these two models crashed: 7 of 7, 3 of 3, 6 of 6 and 4 of 4 in Crashlytics' per-device totals. A real user population never crashes at 100%.

On Oct 23 the public couldn't install 3.42.1 yet. The two devices took turns, installing fresh roughly every 10–30 minutes. Each dot below is one install, with hover for its crashes.

4Every build gets the same burst, right after it's built›

This isn't specific to 3.42.1. Since August, almost every build shows the same two devices crashing in a burst of a few hours. That includes builds Crashlytics only ever saw on about 10 devices. That's how a review or test pipeline behaves: it runs once per submitted build. It also explains why Crashlytics keeps flagging these issues as regressed after they're closed.

5Each install crashes 1–3 times within seconds, then is never seen again›

8Why a bot reaches these screens and a person doesn't›

Both screens belong to libraries. MAMResolverActivity is part of the Intune SDK, and YubiKeyPromptActivity is part of YubiKit, which MSAL pulls in for smart-card sign-in. Neither can be opened from outside the app (the SDK manifest declares exported="false"). Both stack traces start with Android re-creating the screen in a fresh process:

Caused by: java.lang.NullPointerException
  at com.yubico.yubikit.android.ui.YubiKeyPromptActivity.onMAMCreate (YubiKeyPromptActivity.java:210)
  at com.microsoft.intune.mam.client.app.offline.OfflineActivityBehavior.onCreate (OfflineActivityBehavior.java:122)
  at com.microsoft.intune.mam.client.app.MAMActivity.onCreate (MAMActivity.java:80)

The SDK's in-memory state is gone at that point, so the screen finds a null value and crashes. Automated testers kill and restore the app constantly to look for crashes. A clinician almost never gets the process killed while one of these short-lived screens is open. The noHistory="true" we already set on MAMResolverActivity can't help, because it only stops a screen being restored after the user has left it.

What we're doing about it

Nothing in the app. The crash is in third-party code, and only an automated tester triggers it.

Reporting: label these issues "Play review automation, 0 real users" and leave them out of the weekly crash-free rate. Together the six Intune/MSAL startup crashes on these two devices hit roughly 1 percentage point of weekly crash-free users. When a closed issue reopens after a release, check Android vitals. If the crash isn't there, it's the same noise.

We considered turning Crashlytics off on emulators. We rejected it: it would only catch the x86 device, not the Huawei, and it would stop crash reports from real x86 users such as Chromebooks.
